# Internationalization architecture

Target locale set: `fr-FR`, `en`, `nb-NO`, `zh-CN`. As of this writing **only fr and en are enabled** — nb-NO and zh-CN are fully wired into the architecture (types, routing utilities, hreflang, the switcher, structured data, Content Graph, Content Integrity) but have zero pages and zero translated strings. Nothing about this document describes working nb/zh pages; it describes the plumbing that's ready for them.

## Locale registry — the single source of truth

`src/i18n/locales.ts` is the only place a locale is defined. Nothing else in the codebase hardcodes a locale list, a BCP 47 tag, a native name, or an `<html lang>` value.

```ts
export type LocaleCode = "fr" | "en" | "nb" | "zh";

LOCALES.fr = { htmlLang: "fr", hreflang: "fr-FR", nativeName: "Français", pathPrefix: "", enabled: true,  ... }
LOCALES.en = { htmlLang: "en", hreflang: "en",    nativeName: "English",  pathPrefix: "en", enabled: true,  ... }
LOCALES.nb = { htmlLang: "nb", hreflang: "nb-NO", nativeName: "Norsk",    pathPrefix: "nb", enabled: false, ... }
LOCALES.zh = { htmlLang: "zh-CN", hreflang: "zh-CN", nativeName: "中文",  pathPrefix: "zh", enabled: false, ... }
```

`htmlLang` and `hreflang` are deliberately different for fr and nb: hreflang benefits from market specificity (`fr-FR`, `nb-NO`), while `<html lang>` is kept as general as correctly possible (`fr`, `nb`) — except zh, where "zh" alone is genuinely ambiguous between Simplified and Traditional, so both values are `zh-CN`.

`enabled: false` is the mechanism that keeps nb/zh completely invisible on the live site — see "What `enabled` actually gates" below.

## `Lang` — one type, four members

`src/i18n/ui.ts` re-exports `Lang = LocaleCode`. Every prop typed `lang: Lang` across the codebase now accepts all four values at the type level. This is intentional and was the main source of ripple-effect type errors fixed while building this (see "What broke and how it was fixed").

## What `enabled` actually gates

`ENABLED_LOCALE_CODES` (derived from the registry, currently `["fr", "en"]`) is the list every loop that produces *visible, live* output reads from:

- `languages` (`src/i18n/ui.ts`) — native names for enabled locales only. `getLangFromUrl`, `switchLocalePath`, and the sitemap-relevant "which locale prefixes exist" logic all key off this.
- `otherEnabledLocales(lang)` (`src/i18n/utils.ts`) — the language switcher's candidate list.
- Content Integrity's R4 (translation coverage) loops over `ENABLED_LOCALE_CODES` only.

Nothing loops over the full `LOCALES` registry for anything user-facing. This is why adding nb/zh to the registry changed zero visible behavior for fr/en — verified by rebuilding and diffing every previously-checked page's hreflang, canonical, `<html lang>`, Open Graph, and structured data.

## The `translations` map — replacing the old binary `altLangHref`

Previously (`altLangHref?: string`), a route could only say "here's one fallback URL" or "nothing, use the naive slug swap." That doesn't generalize past two locales. `TranslationMap = Partial<Record<Lang, string>>` (`src/i18n/utils.ts`) replaces it everywhere: `Seo.astro`, `BaseLayout.astro`, `Header.astro`, `LanguageSwitcher.astro` all take `translations?: TranslationMap` and resolve it through one function, `resolveTranslations()`, so the switcher and hreflang can never disagree about which locales a page is actually available in.

**The contract that matters** (documented in code, repeated here because a violation of it caused a real regression while building this — see below):

- `translations` **omitted** (`undefined`) — the route never checked per-locale availability; assume the naive same-slug swap is valid for every enabled locale. Correct default for static pages (About, Contact, division pages, …).
- `translations` **explicitly `{}`** — the route checked and found no translation anywhere. Every locale is reported unavailable.
- `undefined` and `{}` are NOT interchangeable. A route that computes translations must always pass a map, even an empty one, once it has actually looked.

## Content identity, not slugs — the Content Graph connection

`src/lib/content-graph.ts`'s `resolveContentId(type, lang, slug)` and its hand-verified `CONTENT_ID_ALIASES` table (built in the Content Graph phase, generalized here from a hardcoded fr/en pair to `Partial<Record<Lang, string>>`) are now the actual mechanism `journal/[slug].astro` / `en/journal/[slug].astro` use to find a page's translation — not raw slug matching. This is why the NTA journal article (FR and EN slugs genuinely differ) now correctly shows reciprocal hreflang and a working switcher link, where before this phase it showed neither (the E-2/D-1 fix correctly *suppressed* the broken hreflang, but nothing *found* the real pair — this phase does).

Adding an alias remains a deliberate, hand-verified, non-guessed decision — see `docs/content-graph.md`, "Adding an alias." Nothing here inferred one automatically.

## SEO surfaces — what each one does now

- **hreflang** (`Seo.astro`): self + every resolved alternate, using each locale's `hreflang` tag from the registry. Omitted entirely (no self, no alternates, no x-default) when zero alternates resolve — the E-2/D-1 behavior, generalized and re-verified intact.
- **canonical**: always the current page's own URL, untouched by any of this.
- **x-default**: the default locale's (`fr`) resolved URL when known, else the current page's own URL. Never a guess.
- **`<html lang>`** (`BaseLayout.astro`): `LOCALES[lang].htmlLang` — `fr`, `en`, `nb`, or `zh-CN`, never the literal string `"no"` (Norwegian's ISO 639-1 macrolanguage code, explicitly not used per the brief — Bokmål is `nb`).
- **Open Graph** (`og:locale`, `og:locale:alternate`): `ogLocaleFor()` derives `xx_XX` from the hreflang tag (`fr-FR` → `fr_FR`, `en` → `en`). One `og:locale:alternate` tag per resolved alternate (was hardcoded to exactly one before).
- **schema.org `inLanguage`** (Organization/WebSite in `Seo.astro`, Article in `JournalDetail.astro`): `LOCALES[lang].hreflang`, same source of truth as hreflang — no separate hardcoded ternary anymore.
- **Sitemap**: unaffected — it's driven entirely by which page files exist (`getStaticPaths()` output), not by the locale registry. No nb/zh routes exist yet, so none appear; this needs no further change to stay correct once they do.

## Typography

- **French, English, Norwegian (Bokmål)**: no change needed. Verified directly in the installed font packages — both Fraunces (`full.css` subset) and Manrope ship a base Latin subset covering `U+0000–00FF`, which includes æ/ø/å (U+00E6/00F8/00E5). Bokmål renders correctly in the existing type stack today, untested-in-production but not blocked by anything.
- **Chinese (Simplified)**: neither font ships any CJK subset — bundling one (routinely 1–10MB+, even subsetted) purely for a locale with zero live pages would be a real, needless performance cost. `src/styles/global.css` scopes a system-font fallback (`PingFang SC`, `Microsoft YaHei`, `Noto Sans CJK SC`, `Heiti SC`) to `:lang(zh)`, which matches `<html lang="zh-CN">` and everything under it — verified via CDP that fr/en pages' `--font-display` still resolves to Fraunces, unaffected.

## Dates and numbers

Every hardcoded `lang === "fr" ? "fr-FR" : "en-US"` (or `"en-GB"`) ternary found across the codebase — `JournalDetail.astro`, `JournalPreview.astro`, `CardJournal.astro`, `CommentSection.astro`, `LivePlayer.astro`, both `journal/index.astro` pages, and the client-side `scroll-choreography.ts` counters — now goes through `intlTagFor(lang)` (server-side) or reads `document.documentElement.lang` directly (client-side, since it's already a valid BCP 47 tag). None of these hardcode a format string; `Intl`/`toLocaleDateString`/`toLocaleString` do the actual formatting natively, so nb-NO and zh-CN dates/numbers will format correctly the moment those locales render anything, with zero further code change.

## Content Integrity extensions

Two new checks in `scripts/content-integrity.mjs`, both reusing `src/i18n/locales.ts` and `src/lib/content-graph.ts` directly (Node 22+'s type-stripping, `--experimental-strip-types`, now used by the `npm run integrity` script) rather than duplicating any logic:

- **Unknown locale** (ERROR): a document's `lang` field must be one of the four registered codes.
- **Stale content-identity alias** (ERROR): every `(locale, slug)` pair declared in `CONTENT_ID_ALIASES` must correspond to a document that actually exists — an alias is a human claim; if it stops being true (a slug renamed, a document unpublished), that's now caught instead of silently trusted.

R4 (translation coverage) was rewritten to loop over `ENABLED_LOCALE_CODES` generically (was hardcoded fr/en) and to match by `resolveContentId`, not raw slug — confirmed by re-running the tool: the NTA journal pair no longer appears as "untranslated" (it's correctly matched via the alias), while the genuinely untranslated `crise-du-luxe` article and both FR-only partners are still correctly flagged. No new findings were introduced by this phase's changes to real content — the same errors/warnings the tool already knew about (invalid partner slug, broken Facebook-URL image, hotlinked Pinterest image) are unchanged.

## Enabling a locale (nb or zh) — the actual future steps

None of this happens automatically. In order:

1. Content exists and is reviewed for the priority pages (Home, About, Services, Selected Work, Journal, Contact — per the brief's own ordering) — in real, professionally-adapted Bokmål or Simplified Chinese, not machine translation and not a literal rendering of the French.
2. `src/i18n/ui.ts`'s `nb`/`zh` dictionaries are filled in key by key (they start as empty objects that fall back to French — see `useTranslations`) — only for the keys actually used by the pages being launched, not all 300+ at once.
3. Page files are created following the established convention (`src/pages/nb/<route>.astro`, `src/pages/zh/<route>.astro` — no dynamic `[lang]` routing anywhere in this codebase, and this phase doesn't change that).
4. `LOCALES.nb.enabled` / `LOCALES.zh.enabled` flips to `true` in `src/i18n/locales.ts` — this single change is what makes the locale appear in the switcher, hreflang, and everywhere else that reads `ENABLED_LOCALE_CODES`.
5. `astro.config.mjs`'s `i18n.locales` array — currently still `['fr', 'en']`, deliberately not touched in this phase since nothing calls Astro's own `astro:i18n` helpers for nb/zh yet (`Seo.astro` was rewritten during this phase to build locale-prefixed URLs manually from the registry instead, specifically so it wouldn't depend on Astro's i18n config knowing about a locale that doesn't have pages yet) — needs updating once real nb/zh routes exist, if anything in the codebase starts calling `astro:i18n` helpers with those codes.
6. `npm run integrity` and `npm run build` + `astro check`, same as any other content change.

## What broke and how it was fixed (worth knowing before touching this again)

Widening `Lang` from two values to four surfaces every place a `Record<Lang, X>` assumed exactly fr/en would ever be indexed. `astro check` caught two real cases (`src/data/founder-bio.ts`'s `founderBio`, `src/lib/search.ts`'s `STATIC_PAGES`) — both fixed by typing them `Partial<Record<Lang, X>>` with an explicit fallback to `defaultLang` at the point of use, not by inventing nb/zh content to satisfy the type checker. A third, subtler case (`src/data/live.ts`'s `LocalizedText`) needed the same treatment plus a small `localizedText()` helper, since it's read from a plain object literal rather than a lookup function.

Separately — not a type error, a real behavioral regression caught only by manually re-diffing every previously-verified page's hreflang output after the change: the FR-only `crise-du-luxe` journal article briefly started claiming a (nonexistent) EN translation again, because `journal/[slug].astro` passed `translations: undefined` for "no match found," which `resolveTranslations()` correctly-by-design treats as "not checked, use the naive swap" rather than "checked, found nothing." Fixed by having the route pass `{}` instead of `undefined` once it has actually looked — see "The `translations` map" above. Re-verified against every previously-checked page afterward; the regression window never reached a build that was proposed for commit.
