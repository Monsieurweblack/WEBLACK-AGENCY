# Internationalization (i18n)

WEBLACK is **exclusively bilingual**: French (`fr`, default locale, site root) and English (`en`, `/en/` prefix). Norwegian (`nb`) and Simplified Chinese (`zh`) were retired on 2026-11-04 by product decision — see "Migration register" below.

## Locale registry — the single source of truth

`src/i18n/locales.ts`:

```ts
export type LocaleCode = "fr" | "en";

LOCALES.fr = { htmlLang: "fr", hreflang: "fr-FR", nativeName: "Français", pathPrefix: "",   shortLabel: "FR" }
LOCALES.en = { htmlLang: "en", hreflang: "en",    nativeName: "English",  pathPrefix: "en", shortLabel: "EN" }
```

Nothing else hardcodes a locale list, a BCP 47 tag or a native name. `htmlLang` and `hreflang` differ for French on purpose: hreflang carries the market (`fr-FR`), `<html lang>` stays as general as correct (`fr`).

`src/i18n/ui.ts` re-exports `Lang = LocaleCode` and holds one full dictionary per locale (`ui.fr`, `ui.en`, both `Record<UiKey, string>`). `LOCALE_CODES` is what every loop over "the locales this site serves" reads: the language switcher (`otherLocales()`), URL-prefix parsing (`languages`), hreflang, and Content Integrity's translation-coverage check (R4).

## The `translations` map

`TranslationMap = Partial<Record<Lang, string>>` (`src/i18n/utils.ts`) is taken by `Seo.astro`, `BaseLayout.astro`, `Header.astro` and `LanguageSwitcher.astro`, and resolved through one function, `resolveTranslations()`, so the switcher and hreflang can never disagree.

- `translations` **omitted** — the route never checked per-locale availability; the naive same-slug swap applies. Correct for static pages (home, About, Contact, division pages…), which all exist in FR and EN.
- `translations` **explicitly `{}`** — the route checked and found no translation. The other locale is reported unavailable: no switcher link, no hreflang.
- The two are NOT interchangeable. A route that computes translations (journal, work, agenda, talent detail…) must always pass a map, even an empty one. No English version is ever invented for content that has none.

## Content identity, not slugs

`src/lib/content-graph.ts`'s `resolveContentId(type, lang, slug)` and its hand-verified `CONTENT_ID_ALIASES` table are how content routes find a page's translation when FR and EN slugs differ. Adding an alias is a deliberate, verified decision — see `docs/content-graph.md`.

## SEO surfaces

- **hreflang** (`Seo.astro`): self + the resolved alternate (`fr-FR`, `en`) + `x-default` (the French URL when known). Omitted entirely when no alternate resolves.
- **canonical**: always the page's own URL.
- **`<html lang>`** (`BaseLayout.astro`): `fr` or `en`.
- **Open Graph**: `og:locale` via `ogLocaleFor()` (`fr_FR`, `en`), one `og:locale:alternate` per resolved alternate.
- **schema.org `inLanguage`**: `LOCALES[lang].hreflang`.
- **Sitemap**: driven by the page files that exist; only FR and EN pages exist.

## Dates and numbers

All formatting goes through `intlTagFor(lang)` (`fr-FR`, `en`) or `document.documentElement.lang` client-side — never a hardcoded format string.

## Content Integrity

`scripts/content-integrity.mjs` reuses the registry and the Content Graph directly:

- **Unknown locale** (ERROR): a document's `lang` must be `fr` or `en`. Verified 2026-11-04: Sanity holds no document in any other language.
- **Stale content-identity alias** (ERROR): every aliased `(locale, slug)` must exist.
- **R4, translation coverage**: loops over `LOCALE_CODES`, matching by content identity, not raw slug.

## Migration register — retired locales (2026-11-04)

Inventory taken before removal: production served exactly four NB/ZH pages, listed in the sitemap and linked from the language switcher and hreflang of `/`, `/en/`, `/about/` and `/en/about/`. No other NB/ZH path ever existed (`/zh-cn/`, `/no/`, nested `/nb/…` pages all answered 404). Sanity holds no NB/ZH document; nothing was deleted there.

| Old URL | Status before | Now | Destination |
|---|---|---|---|
| `/nb/` | 200 | 301 | `/en/` |
| `/nb/about/` | 200 | 301 | `/en/about/` |
| `/zh/` | 200 | 301 | `/en/` |
| `/zh/about/` | 200 | 301 | `/en/about/` |
| `/nb`, `/zh` (no slash) | 308 → slash | 301 | `/en/` |
| `/nb/*`, `/zh/*` (never published) | 404 | 301 | `/en/*` (same path) |

Rules live in `public/_redirects` only — not in `astro.config.mjs` `redirects`, which would generate meta-refresh pages under `/nb/` and `/zh/` in the build. Destination is English: for a Norwegian- or Chinese-speaking reader it is the language most likely read, and each target is the exact editorial equivalent (home → home, about → about). The wildcard keeps the path — nothing is sent to the homepage wholesale.

Removed with them: the `nb`/`zh` page files, their partial UI dictionaries, the `:lang(zh)` CJK font fallback, the `enabled` flag and `ENABLED_LOCALE_CODES` (every remaining locale is published), and the explicit translation maps on home/About that only existed to opt those pages into NB/ZH.

`functions/lib/talentOptions.ts` still lists `zh` (and other ISO codes) among the **languages a talent candidate can declare speaking** — application data, not a site locale; deliberately untouched.

## Adding a locale back

A product decision first. Then: real translated pages and content; an entry in `LOCALES`; a full dictionary in `ui.ts`; page files under `src/pages/<code>/` (no dynamic `[lang]` routing in this codebase); `astro.config.mjs` `i18n.locales`; and the matching `_redirects` rules removed.
